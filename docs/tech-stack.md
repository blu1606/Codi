## 2. Why PostgreSQL, and what it costs us

The verified v6 schema is SQL Server T-SQL: 28 tables, 85 CHECK constraints, 59 FKs,
36 indexes, 2 views, 1,245 lines, 21/21 smoke tests green on SQL Server 2022.
Moving to PostgreSQL means porting all of it and retiring the live `Codi` database
along with its SSMS `Diagram_0`.

**What the port actually involves** — mechanical, and bounded:

| Construct | Count | Becomes |
|---|---|---|
| `IDENTITY(1,1)` | 23 | `GENERATED BY DEFAULT AS IDENTITY` |
| `NVARCHAR(n)` / `NVARCHAR(MAX)` | 16 / 28 | `VARCHAR(n)` / `TEXT` — Postgres is UTF-8 natively, so Vietnamese needs no `N` prefix |
| `BIT` | 20 | `BOOLEAN` |
| `DATETIME2(3)` | 67 | `TIMESTAMPTZ(3)` |
| `SYSUTCDATETIME()` | 29 | `NOW()` |
| `GO` batch separators | 46 | removed |
| `ISNULL` | 1 | `COALESCE` |

CHECK constraints, foreign keys, cascades, both filtered unique indexes, and both views
port with identical or near-identical syntax — PostgreSQL partial indexes use the same
`CREATE UNIQUE INDEX ... WHERE ...` form. There is no `TOP`, `IIF`, `GETDATE`, or `OFFSET`.

**What PostgreSQL gives back.** It dissolves the two hardest problems the v6 rebuild fought:

- **`NULL UNIQUE`** — the blocking bug where SQL Server treats NULLs as equal, so only one
  row could hold NULL. PostgreSQL permits multiple NULLs in a UNIQUE constraint. The bug
  cannot occur. Filtered indexes remain useful for performance, not for correctness.
- **Cascade path conflicts** — the 16 linter warnings came from SQL Server's restriction on
  multiple cascade paths. PostgreSQL has no equivalent restriction and resolves delete
  ordering at runtime.

It also lets us close two items the v6 report left open: constraints get explicit names
(so the schema diffs cleanly between machines), and `skill_prerequisites` can enforce
"both skills belong to the same course" declaratively via a composite foreign key, rather
than leaving it to application code.

**Tooling follow-on.** `database/gen_erd.py`, `lint_schema.py`, and `smoke_test.sql` parse
T-SQL and must be updated for the PostgreSQL dialect. The ERD is generated from the schema
file, so it must not be edited by hand.

## 3. Identity — the `users` primary key

> **[2026-09-21 update] Status disputed — do not treat this section as current fact.**
> This decision was verified against source and then apparently not what got built: the
> live Drizzle schema in `packages/db/schema/auth.ts` uses text ids, not the
> `BIGINT GENERATED BY DEFAULT AS IDENTITY` this section specifies, and the table is named
> `user`, not `users`. Nobody has re-verified *why* it changed or which one is actually
> correct against the deployed database — that's plan Phase 8, item 1 (schema reconciliation).
> This section is left intact below as the historical reasoning for the BIGINT-serial
> decision; once Phase 8 resolves which schema wins, rewrite this section to match rather
> than patching it further.

This is the one decision that constrains everything else, because 27 tables carry foreign
keys onto the users table. It was settled empirically against better-auth 1.7.5 source,
not from documentation, because the docs and community reports contradict each other.

**Decisions:**

1. **Rename `users.user_id` → `users.id`**, keeping `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
   Better Auth cannot remap the `id` field name (issue #5807). Renaming the referenced
   column is free during a port we are doing anyway; referencing columns elsewhere keep
   their descriptive names (`learner_id`, `granted_by`, …).
2. **Set `advanced.database.generateId: "serial"`.** This is the real option name.
   `useNumberId` is an internal variable, not config — a stale error string inside the
   library still names it, which is where the confusion originates.
3. **Hand-write the four Better Auth tables** (`user`, `session`, `account`, `verification`)
   into our own migration rather than letting the CLI own them. The CLI emits 32-bit
   `integer` for identity columns (issue #5657); we need `BIGINT` for consistency with the
   other 27 tables. Generated foreign keys default to `ON DELETE CASCADE`.

**Verified behaviour** (read from `@better-auth/core` 1.7.5, not assumed):

| Question | Answer |
|---|---|
| Where is the credential password stored? | On `account`, with `providerId: "credential"` — **not** on `user`. A Google-only account has no credential row, so `users` needs no password column at all. |
| Do `session.userId` / `account.userId` follow the numeric id? | Yes. The generator maps `foreignKeyId` to `integer` in serial mode, so there is no text-vs-bigint mismatch. |
| Does node-postgres returning `BIGINT` as a string break it? | No. The adapter coerces id fields with `Number(value)` on read and input. No custom `pg` type parser is needed for auth tables. Our own Kysely queries on domain tables are a separate decision. |
| Are real FK constraints generated? | Yes, with an `ON DELETE` clause. |

**Consequence for the `users` table.** Better Auth owns these concerns, so the columns are
dropped rather than ported:

| v6 column | Fate |
|---|---|
| `password_hash` | → `account.password` |
| `email_verification_code`, `email_verification_expires_at` | → `verification` table |
| `password_reset_token`, `password_reset_expires_at`, `password_reset_requested_at` | → `verification` table |
| `is_email_verified` → mapped to `emailVerified` · `full_name` → `name` · `avatar_url` → `image` | kept, mapped via `user.fields` |

The filtered index `UX_users_password_reset_token` disappears with its column.

## 4. Deployment — portable by construction

**[2026-09-21 update] Revised target split — dev and production now use different hosts on
purpose, not by drift:**

| Environment | App host | Database host |
|---|---|---|
| Dev | local (`pnpm dev`) | **Supabase** Postgres, free tier |
| Preview/demo | **Vercel** | Supabase (same project, or a branch database) |
| Production, later | **Docker**, self-hosted — exact host not yet chosen | undecided: continue on Supabase, or move to a Docker-adjacent Postgres |

Render is dropped entirely — not used for the app, not used for the database. GCP Cloud Run,
Kubernetes, and a Cloudflare reverse proxy remain later options once the production Docker
target exists. Portability is preserved by *refusing* host-specific primitives, not by an
abstraction layer — a plain `postgres://` connection string and a Dockerfile already reach
every target above.

**Do not use:** `@vercel/kv`, `@vercel/blob`, `@vercel/postgres`, Edge Config, `runtime:
'edge'` — each forks the codebase toward a Vercel-only future. **And do not use
`@supabase/supabase-js`, `@supabase/ssr`, or any Supabase Auth/Storage/Realtime client in
application code.** Confirmed by research, 2026-09-21 (Drizzle's and Supabase's own docs
agree): `supabase-js` is a REST/Realtime wrapper needed only for Auth, Storage, Realtime, or
RLS-scoped client access — none of which this app uses through Supabase (Better Auth handles
auth, R2 handles storage). For plain SQL querying, Drizzle already connects directly via
`drizzle-orm/node-postgres` over `DATABASE_URL` (`packages/db/src/index.ts`), which is the
pattern both Drizzle's and Supabase's docs recommend — adding `supabase-js` on top would be a
second, redundant client for the same queries. If Storage or Realtime genuinely gets adopted
later, wrap it behind the existing `StorageProvider` seam (§5) rather than calling
`supabase-js` directly from feature code — same reasoning as the SDK ban above: it's what
keeps the eventual move to self-hosted Docker Postgres a config change, not a rewrite.

**Supabase CLI** (`supabase/config.toml`, scaffolded 2026-09-21, root `pnpm supabase:*`
scripts) is for **linking to and inspecting the hosted project** — `pnpm supabase:login` then
`pnpm supabase:link -- --project-ref <ref>` — and, if ever needed, running the local emulation
stack (`supabase start`). **It does not own schema migrations here.** `database/migrate.sh` +
`database/schema.sql` (Phase 2's runner) is the one migration path; running `supabase db
push`/`migration new` against the same database would create a third, uncoordinated source of
schema truth alongside that runner and the Drizzle schema in `packages/db` — don't.

**Database hosting.** Supabase free Postgres for dev: 500 MB storage, pauses after 7 days of
inactivity (auto-resumes on the next request, no data loss, ~10-30s cold start) — acceptable
for a project with regular activity. Use the **pooled** ("Transaction pooler", port 6543)
connection string, not the direct one — Next.js dev opens many short-lived connections per
hot reload and will exhaust Supabase's direct-connection cap otherwise. `POSTGRES_HOST_PORT`
and the local `postgres` Docker service still exist (`docker compose --profile local-db up`)
for offline work or for rehearsing the eventual self-hosted setup — they are not the default.

Render's free-tier Postgres (30-day expiry) and Neon were both considered and are no longer
relevant now that dev is Supabase-only and there is no Render app target — noted here only so
the reasoning isn't silently lost if the question comes back up.

**Images.** Install `sharp` in the runtime stage and keep Next.js image optimization enabled.
Setting `unoptimized: true` is the usual self-hosting advice but it is unnecessary and would
hurt the course catalog later.

**Cloudflare, designed in now rather than retrofitted.** Real client IP comes from
`CF-Connecting-IP`, not `X-Forwarded-For`. Better Auth needs `baseURL` plus **`trustedOrigins`**
— note this is the correct option name; `allowedHosts` applies only to dynamic base-URL patterns.

**Config** should be a single Zod-validated env schema, splitting server-only from
`NEXT_PUBLIC_` vars — **[2026-09-21 update]** the shipped app actually uses
`@varlock/nextjs-integration` instead; not yet confirmed whether it gives equivalent
secret-isolation guarantees (see plan Phase 3 as-built note). Local development runs
`docker compose` for **Mailpit only** by default; the `postgres` service is an opt-in profile
now that dev points at Supabase.

## 5. Three seams, and no others

Abstract only where a provider will genuinely be swapped. Everything else is YAGNI.

| Seam | Now | Later | Why it earns an interface |
|---|---|---|---|
| `LlmProvider` | **[2026-09-21 update] not built** — `/api/ai/route.ts` calls Google Gemini directly via the Vercel AI SDK | Gemini, Claude, local, behind the originally planned interface | Explicitly requested. Also lets the AI slice be tested against a deterministic fake, which matters because LLM output is not reproducible. The AI page shipped ahead of the seam — migrate it in when the seam is actually built, don't build the seam speculatively before there's a second provider to justify it. |
| `StorageProvider` | Cloudflare R2 | — | Container filesystems are ephemeral on a self-hosted Docker target and effectively read-only on Vercel, so avatars cannot live on disk in production. R2 free tier is 10 GB with free egress. Uploads are presigned, client-direct. |
| `EmailProvider` | **[2026-09-21 update]** Resend (with a console-log fallback in dev) | — | Verification (OTP) and reset mail. The originally planned Mailpit dev-catcher adapter was not wired up — Resend is used in dev too, falling back to logging the OTP to the console when no API key is set. |

Deployment itself gets **no** abstraction layer — a Dockerfile plus env vars already makes
every target reachable. An internal "platform adapter" would be over-engineering.
