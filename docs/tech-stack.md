# Codi — Technology Stack

Status: approved 2026-09-21 · Supersedes the stack assumptions in the v5→v6 database report.

Codi is an AI-powered programming-learning platform that generates personalized learning
paths. This document records what we build on and, more importantly, *why* — so that a
decision is not silently reversed later by someone who only sees the consequence.

---

## 1. Stack

| Layer | Choice | Why this and not the obvious alternative |
|---|---|---|
| Framework | **Next.js 15**, App Router, TypeScript | One deployable for UI and API. Server Components keep the course catalog cheap to render. |
| Runtime | **Node 24 LTS** | Matches the team's local runtime; the Docker base image is pinned to the same major. |
| Database | **PostgreSQL 16** | Replaces SQL Server — see §2. |
| Data access | **Kysely** over hand-written SQL | The `.sql` schema stays the source of truth. An ORM that owns the schema would drop our 85 CHECK constraints; Prisma ignores them outright. Kysely is types-only and generates no DDL. |
| Auth | **Better Auth 1.7.5** | Ships email verification, password reset, and Google OAuth — the entire first slice. Its internal database layer *is* Kysely, so it shares our connection pool rather than fighting it. |
| Styling | **Tailwind v4 + shadcn/ui** | Tokens in `docs/design-guidelines.md`. |
| Container | **Docker**, `output: 'standalone'` | See §4. |
| LLM | **OpenAI**, behind an interface | See §5. |

Package manager: **pnpm**.

## 2. Why PostgreSQL, and what it costs us

The verified v6 schema is SQL Server T-SQL: 28 tables, 85 CHECK constraints, 59 FKs,
36 indexes, 2 views, 1,245 lines, 21/21 smoke tests green on SQL Server 2022.
Moving to PostgreSQL means porting all of it and retiring the live `Codi` database
along with its SSMS `Diagram_0`.

**What the port actually involves** — mechanical, and bounded:

| Construct | Count | Becomes |
|---|---|---|
| `IDENTITY(1,1)` | 23 | `GENERATED BY DEFAULT AS IDENTITY` |
| `NVARCHAR(n)` / `NVARCHAR(MAX)` | 16 / 28 | `VARCHAR(n)` / `TEXT` — Postgres is UTF-8 natively, so Vietnamese needs no `N` prefix |
| `BIT` | 20 | `BOOLEAN` |
| `DATETIME2(3)` | 67 | `TIMESTAMPTZ(3)` |
| `SYSUTCDATETIME()` | 29 | `NOW()` |
| `GO` batch separators | 46 | removed |
| `ISNULL` | 1 | `COALESCE` |

CHECK constraints, foreign keys, cascades, both filtered unique indexes, and both views
port with identical or near-identical syntax — PostgreSQL partial indexes use the same
`CREATE UNIQUE INDEX ... WHERE ...` form. There is no `TOP`, `IIF`, `GETDATE`, or `OFFSET`.

**What PostgreSQL gives back.** It dissolves the two hardest problems the v6 rebuild fought:

- **`NULL UNIQUE`** — the blocking bug where SQL Server treats NULLs as equal, so only one
  row could hold NULL. PostgreSQL permits multiple NULLs in a UNIQUE constraint. The bug
  cannot occur. Filtered indexes remain useful for performance, not for correctness.
- **Cascade path conflicts** — the 16 linter warnings came from SQL Server's restriction on
  multiple cascade paths. PostgreSQL has no equivalent restriction and resolves delete
  ordering at runtime.

It also lets us close two items the v6 report left open: constraints get explicit names
(so the schema diffs cleanly between machines), and `skill_prerequisites` can enforce
"both skills belong to the same course" declaratively via a composite foreign key, rather
than leaving it to application code.

**Tooling follow-on.** `database/gen_erd.py`, `lint_schema.py`, and `smoke_test.sql` parse
T-SQL and must be updated for the PostgreSQL dialect. The ERD is generated from the schema
file, so it must not be edited by hand.

## 3. Identity — the `users` primary key

This is the one decision that constrains everything else, because 27 tables carry foreign
keys onto the users table. It was settled empirically against better-auth 1.7.5 source,
not from documentation, because the docs and community reports contradict each other.

**Decisions:**

1. **Rename `users.user_id` → `users.id`**, keeping `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
   Better Auth cannot remap the `id` field name (issue #5807). Renaming the referenced
   column is free during a port we are doing anyway; referencing columns elsewhere keep
   their descriptive names (`learner_id`, `granted_by`, …).
2. **Set `advanced.database.generateId: "serial"`.** This is the real option name.
   `useNumberId` is an internal variable, not config — a stale error string inside the
   library still names it, which is where the confusion originates.
3. **Hand-write the four Better Auth tables** (`user`, `session`, `account`, `verification`)
   into our own migration rather than letting the CLI own them. The CLI emits 32-bit
   `integer` for identity columns (issue #5657); we need `BIGINT` for consistency with the
   other 27 tables. Generated foreign keys default to `ON DELETE CASCADE`.

**Verified behaviour** (read from `@better-auth/core` 1.7.5, not assumed):

| Question | Answer |
|---|---|
| Where is the credential password stored? | On `account`, with `providerId: "credential"` — **not** on `user`. A Google-only account has no credential row, so `users` needs no password column at all. |
| Do `session.userId` / `account.userId` follow the numeric id? | Yes. The generator maps `foreignKeyId` to `integer` in serial mode, so there is no text-vs-bigint mismatch. |
| Does node-postgres returning `BIGINT` as a string break it? | No. The adapter coerces id fields with `Number(value)` on read and input. No custom `pg` type parser is needed for auth tables. Our own Kysely queries on domain tables are a separate decision. |
| Are real FK constraints generated? | Yes, with an `ON DELETE` clause. |

**Consequence for the `users` table.** Better Auth owns these concerns, so the columns are
dropped rather than ported:

| v6 column | Fate |
|---|---|
| `password_hash` | → `account.password` |
| `email_verification_code`, `email_verification_expires_at` | → `verification` table |
| `password_reset_token`, `password_reset_expires_at`, `password_reset_requested_at` | → `verification` table |
| `is_email_verified` → mapped to `emailVerified` · `full_name` → `name` · `avatar_url` → `image` | kept, mapped via `user.fields` |

The filtered index `UX_users_password_reset_token` disappears with its column.

## 4. Deployment — portable by construction

Targets now: **Vercel** (preview/demo) and **Render** running the Docker image.
Targets later: GCP Cloud Run, Kubernetes, behind a Cloudflare reverse proxy.
Portability is preserved by *refusing* host-specific primitives, not by an abstraction layer.

**Do not use:** `@vercel/kv`, `@vercel/blob`, `@vercel/postgres`, Edge Config, or
`runtime: 'edge'`. Each has no Render or Cloud Run equivalent and would fork the codebase.

**Database hosting.** Render's free PostgreSQL **expires after 30 days with no auto-renew** —
it would vanish mid-semester. Use **Neon** or **Supabase** free Postgres, which do not expire,
and treat Render as an application host only. Both are reached through the same `DATABASE_URL`,
so this is not a lock-in.

**Images.** Install `sharp` in the runtime stage and keep Next.js image optimization enabled.
Setting `unoptimized: true` is the usual self-hosting advice but it is unnecessary and would
hurt the course catalog later.

**Cloudflare, designed in now rather than retrofitted.** Real client IP comes from
`CF-Connecting-IP`, not `X-Forwarded-For`. Better Auth needs `baseURL` plus **`trustedOrigins`**
— note this is the correct option name; `allowedHosts` applies only to dynamic base-URL patterns.

**Config** is a single Zod-validated env schema, splitting server-only from `NEXT_PUBLIC_` vars.
Local development runs `docker compose`: app + Postgres 16 + Mailpit as a mail catcher.

## 5. Three seams, and no others

Abstract only where a provider will genuinely be swapped. Everything else is YAGNI.

| Seam | Now | Later | Why it earns an interface |
|---|---|---|---|
| `LlmProvider` | OpenAI | Gemini, Claude, local | Explicitly requested. Also lets the AI slice be tested against a deterministic fake, which matters because LLM output is not reproducible. |
| `StorageProvider` | local disk (dev) | Cloudflare R2 | Container filesystems are ephemeral on Render and effectively read-only on Vercel, so avatars cannot live on disk in production. R2 free tier is 10 GB with free egress. Uploads are presigned, client-direct. |
| `EmailProvider` | Mailpit (dev) | Resend (3k/month free) | Verification and reset mail must be inspectable locally without sending real email. |

Deployment itself gets **no** abstraction layer — a Dockerfile plus env vars already makes
every target reachable. An internal "platform adapter" would be over-engineering.

## 6. Open

1. **Brand colour.** Design proposes teal `oklch(0.52 0.128 207)`. Does the SWP391 brief
   mandate an existing Codi logo or palette that overrides it?
2. **Locale.** Vietnamese-first UI with English content, or a bilingual switcher? Affects
   `lang`, font subsetting, and button string budgets.
3. **Google sign-in is not in the UC model.** Tab 2 has only `Sign In`. It needs either a new
   use case or a documented alternate flow, plus an RDS update — the UC count is currently
   reconciled at 47 and a script asserts diagram-to-document match.
4. **Account-linking policy.** Two live Better Auth bugs affect the exact case where a user
   registers with email/password, never verifies, then signs in with the same Google address
   (#11321, #11138). We must pick a deliberate behaviour rather than discover it in the demo.
