# Codi PostgreSQL port and authentication slice

## Overview

Codi has a complete, verified design layer and no code. This plan turns that design into a
running application: it ports the schema to PostgreSQL, scaffolds the Next.js 15 app, and
delivers authentication end to end as the first demonstrable slice.

Stack rationale and the resolved identity decision live in [`docs/tech-stack.md`](../../docs/tech-stack.md).
Design tokens live in [`docs/design-guidelines.md`](../../docs/design-guidelines.md).
Do not re-litigate those decisions here.

**What already exists and must not be broken:** the use case model
(`UC-by-actor.drawio`, 47 use cases reconciled against the RDS by script), the verified
schema (`database/schema-v6.sql`, 28 tables / 85 CHECKs / 59 FKs, 21/21 smoke tests green
on SQL Server 2022), and three prior design reports under `plans/reports/`.

## Scope boundary

**In scope:** everything above, plus updating `gen_erd.py`, `lint_schema.py`, and
`smoke_test.sql` for the PostgreSQL dialect.

**Explicitly out of scope:** course catalog, enrollment, payment, the AI/BKT layer, and
the remaining 40 use cases. The schema supports them; no UI or API for them is built here.

## Success criteria

- [ ] `docker compose up` plus `./database/migrate.sh --seed` yields a working app and a
      populated database, from a clean clone, without anyone being asked how
- [ ] Ported schema applies cleanly; the ported smoke test passes at parity with the SQL Server run
- [ ] `alice@x` and `Alice@x` are the same account — the case-sensitivity regression is closed
- [ ] `lint_schema.py` reports clean on the PostgreSQL schema
- [ ] ERD regenerated from the ported schema; no hand edits
- [ ] A user can register, receive a verification mail in Mailpit, verify, sign in, and reach a protected page
- [ ] A protected page checks an actual role, not merely that a session exists
- [ ] `pnpm test` and `pnpm test:e2e` run in CI and gate the build
- [ ] A user can sign in with Google and with GitHub, and linking behaves per the decided policy
- [ ] A user can change password, reset a forgotten password, edit their profile, and change their avatar
- [ ] UI switches between Vietnamese and English without a reload loop
- [ ] The same commit deploys to Vercel and builds as a container

## Red-team findings folded in

Two adversarial reviews ran before this plan was finalised
(`plans/reports/*redteam*`, `*red-team-security*`). What changed:

| Finding | Severity | Resolution |
|---|---|---|
| **Email case-sensitivity regression** — SQL Server's default collation is case-insensitive, PostgreSQL is not, so the port would start accepting `Alice@x` and `alice@x` as two accounts | Critical | Phase 2: unique index on `lower(email)` + normalise on write |
| Test infrastructure named in success criteria but installed by no phase | Critical | Phase 3 now owns Vitest + Playwright setup |
| No migration runner — `docker compose up` left an empty database | Critical | Phase 1 adds the runner; Phase 2 wires seed into it |
| `roles` seed not guaranteed before the Phase 4 role hook runs | Critical | Phase 2 seed, applied by the runner, verified in Phase 1 criteria |
| Account-enumeration prevention asserted but not specified | Critical | Phase 4 specifies the response contract explicitly |
| Email-verification state after OAuth auto-link left undefined | Critical | Phase 5 decides it; see open question 1 |
| `create-next-app` overwrite mitigated only by review discipline | High | Phase 1 no longer creates Node artifacts — conflict removed structurally |
| Authorization stops at "is signed in"; roles never checked | High | Phase 4 adds a role-check helper and applies it |
| Better Auth BIGINT FKs unverified at schema-lock time | High | Phase 2 verifies at lock, not in Phase 4 |
| Effort underestimated ~1 week | High | Re-estimated above: 4-5 weeks |

Rejected: the reviewers' concern that `DATETIME2`→`TIMESTAMPTZ` broadly changes CHECK
semantics. The timestamp CHECKs in v6 are relative comparisons (`revoked_at >= granted_at`),
which are timezone-invariant. Phase 2 still pins the session timezone to UTC when applying,
because *input interpretation* does differ — but this is a narrower risk than reported.

## Open questions

1. **After OAuth auto-links to an unverified password account, is that account now verified?**
   Google and GitHub both assert a verified address, so treating it as verified is defensible
   and is what makes the flow usable. It also closes the pre-registration window the auto-link
   decision opened. Needs an explicit answer before Phase 5 — proposing *yes, mark verified*.
2. **UC model update.** Google and GitHub sign-in are being treated as alternate flows
   inside `Sign In`, keeping the count at 47. Confirm before the RDS is regenerated.
3. **Who hosts Postgres** — Neon or Supabase? Either works; the team should pick one and
   share the connection string.
4. **Does the SWP391 deliverable require the SQL Server schema to remain in the report?**
   If so, the ported file needs a short appendix explaining the migration rather than a
   silent replacement.
5. **Is an auth-only first milestone right for the grading panel?** The project is titled
   around AI personalization. Auth is the correct *engineering* foundation, but a panel may
   expect to see something course-shaped. Worth deciding now whether a thin catalog view
   should be pulled forward.
