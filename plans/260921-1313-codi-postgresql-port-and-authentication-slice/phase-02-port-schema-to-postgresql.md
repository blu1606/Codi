# Phase 2: Port schema to PostgreSQL

## Overview

Translate the verified 28-table SQL Server schema to PostgreSQL without losing any of the
integrity it encodes, add the three Better Auth tables, and re-point the ERD and linter
tooling at the new dialect.

## Requirements

- Functional: all 28 domain tables, 85 CHECK constraints, 59 FKs, 36 indexes, and 2 views
  exist in PostgreSQL with equivalent semantics.
- Functional: three Better Auth tables (`session`, `account`, `verification`) with real
  foreign keys onto `users`.
- Non-functional: the ERD is generated from the schema file, never hand-edited.
- Non-functional: equivalence is demonstrated by a passing test run, not by inspection.

## Architecture

**Source of truth:** `database/schema.sql` — the whole current schema, readable, and what
`gen_erd.py` parses.

**Applied artifact:** `database/migrations/001-baseline.sql` — for a greenfield database
this is the same content. Later changes add `002-*.sql` *and* edit `schema.sql`.

Keeping both honest reuses the technique the team already used successfully when migrating
the live `Codi` database (see report §13): apply migrations to one scratch database, apply
`schema.sql` to another, and diff `information_schema`. That diff becomes a CI check rather
than a one-off.

### Mechanical translation

| SQL Server | Count | PostgreSQL |
|---|---|---|
| `BIGINT IDENTITY(1,1)` | 23 | `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| `NVARCHAR(n)` | 16 | `VARCHAR(n)` |
| `NVARCHAR(MAX)` / `VARCHAR(MAX)` | 28 | `TEXT` |
| `BIT` | 20 | `BOOLEAN` (literals `0`/`1` → `false`/`true`) |
| `DATETIME2(3)` | 67 | `TIMESTAMPTZ(3)` |
| `SYSUTCDATETIME()` | 29 | `NOW()` |
| `GO` | 46 | removed |
| `ISNULL(a,b)` | 1 | `COALESCE(a,b)` |
| `N'literal'` | — | `'literal'` |

Unchanged: CHECK constraints, foreign keys, `ON DELETE CASCADE`, both filtered unique
indexes (PostgreSQL partial indexes use the identical `CREATE UNIQUE INDEX ... WHERE ...`
form), both views, and `DECIMAL`.

`BY DEFAULT` rather than `ALWAYS` on identity columns — `ALWAYS` rejects explicit id
inserts, which would break seed scripts and test fixtures.

### The `users` table

Rename `user_id` → `id`. Better Auth cannot remap the `id` field (issue #5807), and
renaming the referenced column during a port we are doing anyway is free. Referencing
columns in the other 27 tables keep their descriptive names — only the `REFERENCES`
target changes.

Drop the columns Better Auth now owns:

| Dropped | Now lives in |
|---|---|
| `password_hash` | `account.password`, `providerId='credential'` |
| `email_verification_code`, `email_verification_expires_at` | `verification` |
| `password_reset_token`, `password_reset_expires_at`, `password_reset_requested_at` | `verification` |

The filtered index `UX_users_password_reset_token` goes with its column. Keep
`is_email_verified`, `full_name`, `avatar_url` — they are mapped, not replaced.

### Better Auth tables

Hand-written, **not** CLI-generated: the CLI emits 32-bit `integer` for identity columns
(issue #5657) and we need `BIGINT` to match the other 27 tables. Verified from
better-auth 1.7.5 source — with `generateId: "serial"`, foreign-key id columns follow the
numeric type, so `session.user_id` and `account.user_id` are `BIGINT REFERENCES users(id)
ON DELETE CASCADE`. Column names are mapped in the Better Auth config, so they stay
snake_case here and match the rest of the schema.

### Email case sensitivity — a regression the port would otherwise introduce

`email VARCHAR(255) NOT NULL UNIQUE` carries no `COLLATE` clause, so under SQL Server it
inherited the database default, which is case-**insensitive**. `Alice@fpt.edu.vn` and
`alice@fpt.edu.vn` therefore collided, which is the correct behaviour for email.

**PostgreSQL is case-sensitive.** A literal port silently starts accepting both as two
separate accounts — two users, two learning histories, and a confusing "email already taken"
that fires only sometimes.

Fix: drop the plain `UNIQUE` on `email` and replace it with

```sql
CREATE UNIQUE INDEX UQ_users_email_lower ON users (lower(email));
```

and normalise to lowercase on write at the application boundary, because Better Auth issues
its own lookups by email and must match the same way. Prefer the functional index over
`CITEXT`: it needs no extension, so it works identically on Neon, Supabase, and a bare
container.

Apply the same treatment to any other address column used for identity lookup.

### Improvements this port enables

Both were left open in the v6 report and are cheap to close while rewriting:

1. **Name every constraint.** SQL Server auto-generated `PK__courses__8F1EF7AE948AAB00`
   style names, so two builds never diffed cleanly. Use `PK_courses`, `UQ_courses_code`.
2. **`skill_prerequisites` same-course integrity.** Add `UNIQUE (skill_id, course_id)` on
   `skills`, then make the prerequisite FKs composite on `(skill_id, course_id)`. This
   enforces declaratively what the v6 report had to leave to application code.

## Implementation Steps

1. Port `schema-v6.sql` → `database/schema.sql` applying the table above. Do this by hand
   or with a throwaway script, but **read every CHECK constraint** — a few compare dates or
   use string functions where dialects differ subtly.
2. Restructure `users` per above; rename `user_id` → `id`; update all 27 FK targets.
3. Append the three Better Auth tables with BIGINT FKs.
4. Name every PK, UNIQUE, and FK constraint.
5. Add the composite-FK fix for `skill_prerequisites` and the `lower(email)` unique index.
6. Copy to `database/migrations/001-baseline.sql`. Write `database/seed.sql` with the three
   roles using `ON CONFLICT DO NOTHING` — the Phase 1 runner re-applies it constantly, and
   Phase 4's registration hook fails without these rows.
6b. **Verify the Better Auth tables before locking the schema.** Source reading confirms
   that with `generateId: "serial"` the foreign-key columns follow the numeric type and reads
   are coerced with `Number()`, but our tables are hand-written as `BIGINT` and have never
   been exercised at runtime. Stand up a throwaway Better Auth instance against this schema
   and complete one signup and one session read. If this is wrong, it is far cheaper to learn
   now than in Phase 4 with UI built on top.
6c. Pin the session timezone to UTC when applying migrations (`SET TIME ZONE 'UTC'`). The
   timestamp CHECKs are relative comparisons and so timezone-invariant, but *input
   interpretation* for `TIMESTAMPTZ` is not, and a developer in `Asia/Bangkok` should not get
   different stored values from CI.
7. Update `lint_schema.py` for PostgreSQL. **Drop the cascade-conflict check** — it modelled
   a SQL Server restriction that does not exist in PostgreSQL; keeping it would report
   phantom problems. Keep orphan-FK and naming checks.
8. Update `gen_erd.py` for the new type names, and regenerate the ERD and exports.
9. Port `smoke_test.sql`. All 21 scenarios must survive, with **one deliberate change**:
   the scenario reproducing the SQL Server `NULL UNIQUE` bug now asserts the *opposite* —
   that PostgreSQL accepts multiple NULLs. Keep it, retitled; it documents why the port
   removed a class of bug.
10. Write the schema/migration parity check as a script for Phase 7 to wire into CI.
    (Kysely type generation moves to Phase 3, which owns the Node toolchain.)

## Success Criteria

- [ ] `psql -f database/migrations/001-baseline.sql` applies with zero errors on a clean DB
- [ ] Object counts match expectation: 31 tables (28 domain + 3 Better Auth), 2 views, ≥85 CHECKs
- [ ] Ported smoke test passes all 21 scenarios, plus a new one proving
      `Alice@x` / `alice@x` are rejected as duplicates
- [ ] `lint_schema.py` reports clean, with no cascade-conflict findings
- [ ] ERD regenerates from `schema.sql`; exports refreshed
- [ ] Parity script reports migrations and `schema.sql` produce identical `information_schema`
- [ ] `seed.sql` is idempotent — applying twice leaves exactly three roles
- [ ] A throwaway Better Auth instance completes signup and session read against the
      hand-written BIGINT tables
- [ ] Every FK targeting `users` resolves to `id`, verified by querying
      `information_schema.referential_constraints`

## Risk Assessment

**Silent CHECK drift** — the highest risk. A CHECK that parses in both dialects but means
something different produces a schema that looks ported and is not. Mitigation: the smoke
test exists precisely to prove constraints *reject* what they should; do not weaken a
scenario to make it pass.

**Renaming `user_id` misses a reference.** 27 tables is enough to miss one. Mitigation: after
applying, query `information_schema.referential_constraints` and assert every FK targeting
`users` resolves to `id`. A missed rename fails at apply time, not silently.

**Better Auth column mapping mismatch.** If the hand-written tables disagree with the config
mapping, failures appear at runtime as missing-column errors during sign-in. Mitigation:
Phase 4 verifies against a real sign-in before anything is built on top.

**Losing the SQL Server artifact.** `schema-v6.sql` is deleted, but it stays in git history
and in the v6 report. If the RDS deliverable needs it, recover it rather than maintaining
two schemas — see open question 3 in `plan.md`.
